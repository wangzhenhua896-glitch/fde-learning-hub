# 全站个性化（自适应）方案可行性论证

> 状态：v3.1，已并入三轮评审（plan-agent / doubao / workbuddy）+ 人类决策「一期零注册」（2026-09-23）
> 起草：kimi，2026-09-23；评审：plan-agent、doubao、workbuddy，2026-09-23
> 背景：用户提出在整个项目贯彻「不同用户目的不同、出发点不同、路径不同」的思想，不只用于诊断环节，且各处粒度应有粗有细。本文论证该思路是否可行、现有素材是否足够、缺什么、怎么补。

---

## 1. 思路重述（被论证对象）

全站个性化 = 一个持续生长的**学习者画像**（声明层 / 诊断层 / 证据层）+ 一组**显式路由规则**，所有环节读写同一画像；粒度原则为「决策代价越大、证据越多，粒度越细」：

| 环节 | 粒度 | 机制 |
|---|---|---|
| 入口分流（目的/背景/时间） | 粗 | 3 问自声明 |
| 项目选择（先做哪个实训） | 中 | 规则推荐，可推翻 |
| 知识诊断 | 细 | 分层题库逐题自适应 + 命名误区 |
| 阶段路径（s1–s7 怎么走） | 细 | 声明+诊断+前序证据综合路由 |
| 阶段内资源定向 | 细 | 误区 → 定向资料 |
| 内容推荐、节奏计划 | 粗 | 简单规则 |

红线：只推荐不隐藏；画像透明可改；推翻事件必须记录并驱动离线规则迭代；不做 IRT 等需要标定数据的伪精确方案。

## 2. 可行性论证

### 2.1 技术可行性：成立，且有先例

- 站点为纯静态 + localStorage，无服务端、无账号。本方案**不需要服务端**：画像、规则引擎、逐题自适应状态机全部可在前端 JS 实现，与现有进度存储（`assets/workbench.js` 的 localStorage 方案）是同一套机制。
- 已有可复用的先例：
  - `profile.js:21-44` 已在做跨项目能力档案聚合——「读取多处存储、聚合成视图渲染」的模式已存在；
  - `workbench.js:40` 的 `DIM_ST` 四态（未评估/有诊断线索/待补充自评/已有自评记录）是现有的能力状态表达。注意：其措辞是**刻意的自评软化**（"已有自评记录"而非"已通过"），本方案的证据层扩展必须保持这个分寸，见 §2.5 的张力讨论；
  - 5 个静态人群路径页（`path-engineer/manager/exec/presales/career`，由 `build_hub.py` 生成，已含 localStorage 打卡）证明「粗粒度分流」在静态站成立，本方案是把它从「写死的阅读路径」升级为「与实训记录联动的动态路径」。
- 技术风险两条：
  1. **题库与答案对客户端可见**，无法用于高利害评估。作为自评/路由工具不构成问题；若未来面向 B 端做付费能力评估，需届时引入服务端判分。配套的**防污染机制**见 §3 G8（低可信线索标记）；
  2. **存储漂移与脆弱性**：`workbench.js:31-35` 已有过一次 legacy key 迁移（`wb_diag` → `wb_diag_{pid}`），说明 schema 演进是现实问题。三层画像必须**从第一天带 schema 版本号与迁移函数**；且 localStorage 可被用户清空，"持续生长的画像"依赖导出备份习惯，需在产品上引导（现有「数据」页导出是现成入口）。

### 2.2 内容可行性：结构够，弹药缺

现有素材的规模（2026-09-23 实测，口径见注）：

| 资产 | 数量 | 对个性化的可用性 |
|---|---|---|
| 实训项目 | 5 个（P1 kb-assistant / P2 ticket-router / P3 bi-agent / P4 sales-qualifier / P5 compliance-agent） | P1 `tier='入门'`，P2–P5 均为「主项目后的场景迁移」，加 `tag` 字段，是项目路由规则的现成输入 |
| 阶段任务包 | 5 × 7 = 35 个阶段，每个含 goal/deliver/checks/rubric(4 项带 hint)/variant/resources(3 条) | rubric 与 checks 可反推阶段前置依赖；35 个 variant 变式题是 L2 分层题的现成富矿 |
| 诊断题 | 5 × 12 = 60 道（6 维 × 2，固定，字段仅 id/dim/q/opts/ans/why） | **大部分**相当于 L2 场景判断；q11（微调 vs RAG 取舍）、q4（检索层 vs 生成层过滤）等已具 L3 权衡性质（doubao/workbuddy 指出，v3 修正）。无分层字段、无误区标注，**仍是最大缺口**（见 §3 G3） |
| 辅导资料链接 | 105 条（35 阶段 × 3），去重后指向 **50 个**目标页（33 专题 + 9 章 + 6 Handbook + book02 + playbook） | 已按阶段挂好；缺「按误区挂」的维度，属映射工作而非内容缺口 |
| 知识底座 | wiki 正文 85 篇（23 章 + 62 专题；含篇章导语与附属页共 93 页）+ 11 篇 Handbook + 13 篇范冰书 + OpenFDE 2 篇 + Awesome 清单 | **足够。不需要再聚合外部内容**，瓶颈从来不在文章数量 |
| 静态人群路径 | 5 个 path-* 页 + orientation 页 | 文案与人群划分可复用为入口分流的初版 |
| 可运行练习 | labs/kb-assistant（14 个测试，本机跑过全绿） | 验证「阶段产出可机器校验」可行，是证据层的试点 |

**结论：个性化所需的「结构素材」（项目元数据、阶段依赖、资源链接、人群划分）已基本齐备；缺的是「标定素材」——分层题目、命名误区、以及它们与资料的映射。**

### 2.3 运营可行性：工作量集中在题库与前端，工期口径（v3 再修订）

- **内容侧**（G1–G6）：分层题库按 2 层口径约 25–35 题 + 每维 1 道 L3 探针，每题含命名误区干扰项 + 资料出处 + 交叉评审，按每题 1–2 人时算为 **5–8 个工作日**；规则表、误区库、依赖图合计 2–3 天。
- **前端侧**（plan-agent 指出 v1 漏估）：逐题自适应状态机、规则引擎、误区报告渲染、路由建议 UI、画像导入导出扩展、防污染标记（G8）、一致性校验（G8），以及每次改动后的 `build_hub.py` 重建 + `test_site.py` 回归，估计 **6–9 个工作日**。
- **试点运营侧**（doubao 指出 v2 漏计）：10 人 × 2 次访谈 + 每周推翻事件归因复盘，约 **2–3 个工作日**，须如实计入。
- **一期合计约 3–4 周**（单人等效，含运营）。
- 维护成本：规则与题库是 `wb_data.py`/`wb_packs.py` 同风格的数据文件，纳入本地 git 流程；但题库每题绑定「依据哪篇资料哪个论断」，**资料修订会带来长期的出处校验维护税**——G8 的机器校验正是为了把这笔税自动化。

### 2.4 商业可行性：服从 90 天验证，不超前投入

- 个性化本身不是卖点，**它服务两个已定的商业目标**：① 提高试点学员完课率（路由不准=浪费时间=流失）；② 误区库与证据档案是未来 B 端「能力验证」产品里别人抄不走的部分。
- 反方风险必须写明：**当前用户数趋近于零，个性化规则没有统计意义上的验证对象**。因此本方案的正当性不来自「提升转化率」，而来自「让 90 天验证期内的 10 个试点学员不被错误路径劝退」。投入上限与此匹配——只做 P1 单项目试点，P2–P5 维持固定题，验证有效再铺开。
- 若 90 天验证不通过，**题库与规则只能算"半沉没"资产**：未经学员数据校正的规则永远是先验猜测；绑定资料出处的题库有持续维护税；在用户数≈0 的项目里维护责任没有承担者。应如实认知，而非宣称"不会沉没"。

### 2.5 与现有「自评非验证」定位的张力（评审新增，未完全解决）

现有产品刻意把一切标为自评：`DIM_ST` 用"已有自评记录"而非"已通过"，界面反复声明"平台不验证、不代表能力"（`workbench.js:82,186`、`profile.js:86,95`）。而本方案的路由建议（"s2 可快速过、s5 重点做"）本质是**用陈述性知识测验结果推断实作路径**——与本方案自己的边界「能力结论永远以阶段证据为准」存在张力。

一期采取的缓解（非解决）：

- 路由建议的措辞一律用「建议/线索」层级，禁止「你已掌握 s3」这类表述；
- `DIM_ST` 语义不动，诊断只影响"线索"态，"通过"类状态仍只由阶段自评证据产生；
- 诊断报告页必须并列显示「这是知识题线索」与「能力以阶段证据为准」两条声明。

**遗留问题（待试点验证）**：当试点学员真的按建议跳级并卡住时，免责声明能否守住信任，还是会被理解为"系统判断失误"？列入试点访谈提纲，见 §5。

### 2.6 总体结论

**有条件可行。** 技术无障碍，结构素材齐备，缺口集中在分层题库、误区库与前端实现，一期约 3–4 周（单人等效，含试点运营）可完成 P1 试点。成立的前提条件：① 投入锁死在 P1 试点，与 90 天商业验证同进退；② §2.5 的定位张力按上述措辞纪律处理并在试点中验证；③ §5 按定性流程执行，不把试点指标当统计结论；④ G8 的防污染标记与一致性校验随一期交付，不加则试点数据不可信、方案在多智能体维护下会静默腐化。四点任一不满足，本结论不成立。

## 3. 素材差距清单与补充方案

按实施顺序排列，「缺口」指现有素材不能直接满足的部分：

### G1. 入口声明问题（无内容缺口，纯设计）
- 需设计 3 问（目的/背景/每周时间）及对应的首页变体文案。5 个 path-* 页的现成文案可裁剪复用。
- 工作量：约 0.5 天（内容）+ 前端约 1 天。无外部素材需求。

### G2. 项目路由规则表（小缺口）
- 缺「人群 × 项目」的显式映射。各项目已有 `tier`/`tag` 字段可作输入，需补一张 `ROUTING` 表（声明组合 → 项目排序 + 理由文案）。
- 工作量：约 0.5 天。**注意：每个推荐必须带一句可解释理由**（「因为你是实施背景，P4 的场景迁移价值最高」），这是红线「可解释」的落地。

### G3. 分层诊断题库（最大缺口）
- 现状：60 道固定题，无 `level`/`misconceptions` 字段；**大部分相当于 L2，但 q11、q4 等已具 L3 权衡性质**（v2「全 L2」判断有误，v3 修正）。
- 粒度（评审收敛）：**试点期按 2 层（L1 概念 / L2 应用）出题；每维度另备 1 道 L3 权衡题作为探针**，收集作答数据但不计入路由。
- 题目素材来源：
  - L1 概念题：从 62 篇专题与各章的核心论断改写（素材充足）；
  - L2 场景题：改造现有 12 题 + 35 个阶段 `variant` 变式题；
  - L3 探针题：**先盘点现有 60 题中已具权衡性质的题（q11、q4 等），改造升级而非新写**，避免重复与层级错位；确需新写时参考 **topic14「LLM 选型与微调实战(LoRA/QLoRA/DPO)」**（v2 误写为 topic11「FDE 项目管理与交付节奏实战」，doubao 发现、workbuddy 复核、kimi 已对照产物页核实修正）、topic58（演示追问）等「取舍类」内容；
  - 每题的 `misconceptions`：以现有 60 题的 `why` 字段为种子扩展（如 q4 的 why 已隐含「生成后捂嘴」误区）。
- 补充方式：智能体起草 → 第二智能体对照原资料核对（防幻觉）→ 人类抽检。每题必须能指出「依据哪篇资料的哪个论断」，禁止凭空编题——topic11 之误正是这条红线存在的理由。
- 工作量：5–8 个工作日（含评审）。

### G4. 命名误区库（从 0 到 1）
- 现状：不存在。这是把「答错了」升级为「你有 X 误区」的核心资产，也是商业上最难被复制的部分。
- 归属（评审收敛）：**独立文件 `misconceptions.py`**。理由：误区是跨项目复用资产（`post_filter` 同时命中 P1 权限过滤与 P5 密级过滤），放进 `wb_data.py`（语义上是 P1 专属）会造成错误归属暗示；`wb_data.py:286` 已有 `from wb_packs import NEW_PACKS` 的聚合先例，误区库照此 import。附带要求：被引用的误区 id 纳入 G8 机器校验。
- 补充方式：先在 P1 六维度各定义 3–5 个命名误区（如 `post_filter`、`frontend_only`、`accuracy_as_goal`），每个含：名称、一句话定义、对应错误选项、定向资料链接。来源：题库 why 字段 + rubric hint 字段（35 阶段 × 4 条 hint，大量已是「典型错误」的表述）。
- 工作量：1–2 天（与 G3 合并进行更高效）。

### G5. 误区 → 资料映射（映射工作，无内容缺口）
- 105 条资源链接（50 个去重目标页）已按阶段挂好；G4 的每个误区从中选 1–2 条定向。工作量：约 0.5 天。

### G6. 阶段依赖图（小缺口）
- 35 个阶段的依赖关系目前只隐含在 s1→s7 的顺序里。阶段路由需要显式依赖图（哪些阶段可跳、哪些有硬前置），可从各阶段 rubric/deliver 反推。
- 工作量：约 0.5 天。

### G7. 证据层的机器校验扩展（中期，非试点必需）
- labs/kb-assistant 证明了「阶段产出可机器校验」。推广到其他项目/阶段是中期工作，**不阻塞个性化试点**，列为二期。

### G8. 防污染标记 + 规则-内容一致性校验（workbuddy 新增，v3 补入）
- **画像防污染**：题库客户端可见，学习者可能按答案刷层。最低成本机制：诊断作答记录每题耗时与改答行为，「异常快答 + 全对」标记为**低可信线索**——只展示、不驱动路由。不加这条，§5 访谈测到的将是作弊率而非规则质量。
- **一致性机器校验**：误区 id、题库出处链接、路由规则引用的阶段 id 都与 `wb_data.py`/`wb_packs.py` 强耦合，内容一改即静默失效。在 `test_site.py` 已有链接检查基建上扩展校验：① 题库引用的误区 id 必须存在于 `misconceptions.py`；② 误区与题库引用的资源 slug 必须命中构建产物页面；③ 路由规则引用的项目/阶段 id 必须存在。边际成本低，随一期交付。
- 工作量：前端防污染约 1 天；校验扩展约 0.5–1 天。

**明确不补的东西**：不再聚合新的外部内容源；不做视频/富媒体；不为个性化引入任何服务端依赖。

## 5. 试点验证：定性流程（评审后修订，不再设定量阈值）

n=10 的样本下任何"显著低于""<20%"式阈值都是伪精确，试点期改用**明确的定性流程**：

1. **访谈对象与时机**：每个试点学员两次——做完诊断后（问"推荐的路径符合你的预期吗？哪里不符"），做完第一个阶段后（问"难度预期准吗？误区报告说中你了吗"）；跳级卡壳者加问 §2.5 遗留问题（"卡住时你觉得是系统判断失误还是自己基础不够"）；
2. **身份与数据回流协议（v3.1 人类决策：一期零注册）**——试点不建账号系统（无服务端、无短信/邮箱验证），身份靠约定而非系统：
   - 每位学员分配编号 **P01–P10**；入口声明（G1）含可选第四项「试点编号」，存入 `wb_profile` 并随导出数据走——即使导出文件名不规范也能从内容认出是谁；
   - 学员全程同一台电脑同一浏览器；换设备走「数据」页导出/导入；一台电脑不混用多名学员；
   - 沟通沉淀靠**私有 CRM 目录 `pilot/`**（只进本地 git，永不进 sync 白名单、永不发布）：每位学员一个文件，任何接触当天记录；沟通渠道用微信群 + 第三方表单（自带合规告知）；
   - **访谈与当场导出绑定**——第二次访谈结束时当场协助学员导出本机数据并收取；明确负责人（试点组织者）、时点（每次访谈现场）、兜底（收不到则该学员数据标记缺失，复盘时只用访谈记录，不事后追讨）；导出文件按 `P03_T1_日期.json` 命名存入 `pilot/exports/`；
   - 升级到注册系统的触发条件（满足任一条再议，预计三期）：学员超约 50 人 / 跨设备连续学习成高频抱怨 / B 端付费评估需可核验身份 / 用户主动要求进度跨端；届时一次性做对（手机验证码需企业主体做短信签名报备，邮箱更便宜但触达率低），不做过渡方案；
3. **推翻事件复盘**：每周汇总收回的推翻记录，逐条人工归因（规则错 / 文案误导 / 用户特例 / 低可信线索干扰），归因结果直接改规则表，不走在线权重调整；
4. **可信度信号**：学员是否愿意把诊断报告/能力档案截图发给他人——这是比完成率更接近产品价值的信号；
5. **复盘节点**：10 人完成或 4 周到期（先到为准），输出一页复盘：哪些规则被推翻、哪些误区被认可、低可信线索占比、§2.5 的措辞纪律是否守住了信任；
6. **二期闸门**：复盘中"规则错"类归因占比过半 → 二期先修规则方法论而非扩题库；误区报告普遍被认可 → 二期优先扩误区库；低可信线索占比高 → 先修防污染再谈其他。

## 6. 已声明的边界（防止后续误解）

- 个性化规则是**作者先验 + 试点校正**，不是统计学习产物；文档与界面须保持此诚实标注；
- 诊断层测陈述性知识，能力结论永远以阶段证据（rubric 逐项 + 可运行产出）为准；路由建议措辞维持「建议/线索」层级（§2.5）；
- 题库客户端可见，不用于高利害场景；异常作答标记为低可信线索、不驱动路由（G8）；
- 画像 schema 从第一天带版本号与迁移函数；localStorage 可丢失，画像以导出文件为准；
- 个性化只做推荐与默认值，不做内容门禁；
- 一期零注册：不建账号系统、不收集账号类个人信息；B 端联系入口为可选邮箱订阅（第三方表单，含合规告知）；升级注册的触发条件见 §5 第 2 条；
- 试点学员的联系方式与访谈记录属个人信息，只存本机 `pilot/` 目录（本地 git），永不发布；
- 题库绑定资料出处，资料修订会产生持续校验维护税，由 G8 机器校验自动化兜底；验证失败时题库与规则按「半沉没资产」如实计。
